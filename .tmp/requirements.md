# 要件定義書 - 訪問順の最適化（ウェイポイント最適化）

## 1. 目的

経路検索で複数の施設を登録したとき、利用者が訪問順を自分で考えなくても、総移動距離が最短になる順序で回れるようにする。

現状は「指定した順に巡る最短経路」しか検索できず、効率のよい順序は利用者がドラッグや「↑」「↓」で並べ替えて試すしかない。Amazon Location Service の `OptimizeWaypoints` API で訪問順を求め、既存の `CalculateRoutes` による経路表示につなげる。

## 2. 機能要件

### 2.1 必須機能

- [ ] **訪問順の最適化ボタン**：経路検索画面の「訪問順」に「訪問順を最適化」ボタンを置く。押すと `OptimizeWaypoints` を呼び、返った順序で一覧（`stops`）を並べ替える。経路の検索は従来どおり画面下部の検索ボタンで行う（最適化と経路検索は別操作）。
- [ ] **出発地の固定**：1番目の地点は常に出発地として固定し、並べ替えの対象にしない。
- [ ] **目的地固定スイッチ**：「最後の地点を目的地として固定」スイッチを置く。
  - オフ（初期値）：出発地以外の全地点を並べ替える。終点は最適化の結果で決まる。
  - オン：1番目と最後の地点を固定し、間の経由地だけを並べ替える。
- [ ] **最適化の基準**：総移動距離が最短になる順序（`OptimizeSequencingFor: ShortestRoute`）。既存の経路検索（`OptimizeRoutingFor: ShortestRoute`）と基準をそろえる。
- [ ] **対応する移動手段**：車・徒歩・スクーター・トラック。公共交通・複合移動では最適化の操作を表示しない（もともと2地点までで、API も非対応）。
- [ ] **利用できる条件の案内**：並べ替える地点が2つ未満のとき（スイッチがオフなら3地点未満、オンなら4地点未満）はボタンを無効にし、必要な地点数を案内する。接続設定が未入力のときも無効にする。
- [ ] **結果のフィードバック**：最適化が完了したら、並べ替えた旨と、API が返す総距離・所要時間の目安を表示する。順序が変わらなかった場合は「すでに最適な順序です」と伝える。
- [ ] **元の順序に戻す**：最適化の直後は「元の順序に戻す」を表示し、1回分だけ取り消せる。その後に地点を追加・削除・手動で並べ替えた時点で、取り消しはできなくなる。
- [ ] **処理中の表示と操作の抑止**：最適化中は進捗表示を出し、ボタンの文言を「最適化中…」にする。地点の追加・並べ替え・削除・移動手段の変更・経路検索は、既存の経路検索中と同じく操作できないようにする。画面を閉じたら通信を中断する。
- [ ] **エラーの案内**：原因ごとに対処がわかる文言を出す。
  - HTTP 403：API キーに `geo-routes:OptimizeWaypoints` の許可が必要であること。
  - 範囲の上限超過（全地点を囲む矩形の周長 500 km）：上限と、地点を減らす・範囲を狭めるという対処。
  - 到達できない地点がある：該当する地点の名前。
  - 通信不可・タイムアウト：既存の経路検索と同じ文言。
  - 応答を読み取れない（順序に全地点が含まれない等）：一覧は変更せず、エラーを表示する。
- [ ] **既存機能との整合**：最適化で一覧が変わったら、表示済みの経路は消える（地点の並べ替えと同じ扱い）。地図上の地点番号は新しい順序に更新される。
- [ ] **README の更新**：API キーに必要なアクションの表、使い方、困ったときの表、料金・送信データの注意事項に、最適化の説明を追加する。
- [ ] **リリース作業**：`metadata.txt` の `version` を上げ、配布用 ZIP を作り直す。

### 2.2 オプション機能（今回は実装しない）

- [ ] 「出発地に戻る」をワンタップで指定する周回モード（今回は、出発地と同じ地点を最後に追加してスイッチをオンにすれば周回できる）。
- [ ] 最適化の基準の切り替え（最短距離／最短時間）。
- [ ] 最適化から経路表示までを1回の操作で行うボタン。
- [ ] 地図タップで地点を追加している画面（地図下部の「経路を検索」）からの最適化。
- [ ] 地点ごとの制約（到着時刻、滞在時間、訪問の前後関係）、交通状況の考慮、近接地点のクラスタリング。
- [ ] 地点ごとの削除ボタン（現状は「末尾の地点を削除」のみ）。

## 3. 非機能要件

### 3.1 パフォーマンス

- 最適化1回につき API 呼び出しは1回。自動再試行や、地点の変更に連動した自動実行はしない（課金対象のため、利用者の操作でのみ実行する）。
- タイムアウトと中断は既存の `LocationRequest`（45 秒、同時に1リクエスト）をそのまま使う。

### 3.2 セキュリティ

- API キーの扱いは現状どおり（端末に保存しない、ログに出さない）。
- 送信するのは地点の座標と移動手段のみ。地点の名前（POI 名・地物名）は送信しない。地点の対応付けに使う ID は連番にする。
- API の応答に含まれる文字列を画面に出す場合は、プレーンテキストとして扱う。

### 3.3 保守性

- リクエストの組み立てと応答の解釈は `Routes.js` の純粋な関数にまとめ、`tests/` の Node テスト（`node --test`）で検証する。QML 側は状態と表示だけを持つ。
- 上限値などの定数は `Routes.js` に1か所で定義し、QML に数値を直接書かない。
- 既存コードの書き方（コメントの密度、命名、`LocationButton` などの共通部品）に合わせる。

### 3.4 互換性

- 最適化を使わない場合の動作は現状から変えない。`geo-routes:OptimizeWaypoints` を許可していない既存の API キーでも、POI 検索と経路検索はこれまでどおり使える。
- QField のプラグイン環境（Qt 6 / QML、外部ライブラリなし）で動作すること。
- ライト／ダークテーマ、スマートフォンの画面幅（既存の最小想定）で操作部が収まり、タップ領域は既存と同じ 44 px 以上を保つ。

## 4. 制約事項

### 4.1 技術的制約

- `OptimizeWaypoints` は順序・総距離・総時間だけを返し、経路の線形は返さない。地図に経路を表示するには、最適化のあとに `CalculateRoutes` が必要。
- 地点数の上限は既存の 25 地点（`CalculateRoutes` の制限）のまま。`OptimizeWaypoints` 側の上限（経由地 50）には達しない。
- `OptimizeWaypoints` の範囲の上限：全地点を囲む矩形の周長が 500 km（実際の呼び出しで確認）。ドキュメントにある「指定順での直線距離の合計 100 km」は、約 170 km の呼び出しが成功したため、判定には使わない。
- 対応する移動手段は Car / Pedestrian / Scooter / Truck のみ。
- この開発環境では QField 実機での動作と、実際の API 応答は確認できない。確認できるのは Node テスト、`qmllint` による静的チェックまで。

### 4.2 ビジネス制約

- `OptimizeWaypoints` は `CalculateRoutes` とは別に課金される。README に明記する。
- 既存の利用者は、API キーに `geo-routes:OptimizeWaypoints` の許可を追加する必要がある。

## 5. 成功基準

### 5.1 完了の定義

- [ ] 3地点以上を登録し「訪問順を最適化」を押すと、出発地を除く地点が最適な順に並び替わる。
- [ ] スイッチをオンにすると、最後の地点が目的地のまま残り、間の地点だけが並び替わる。
- [ ] 「元の順序に戻す」で、最適化前の順序に戻る。
- [ ] 最適化後に検索ボタンを押すと、新しい順序の経路が地図に表示される。
- [ ] 公共交通・複合移動では最適化の操作が表示されない。
- [ ] 許可のないキー、範囲超過、到達できない地点、通信不可のそれぞれで、原因に合った案内が表示され、一覧は変更されない。
- [ ] `Routes.js` に追加した関数の Node テストと、既存のテストがすべて通る。
- [ ] `qmllint` で、今回の変更による新しい警告が出ない。
- [ ] README、`metadata.txt`、配布用 ZIP が更新されている。

### 5.2 受け入れテスト（QField 実機で利用者が確認）

- 現在地を出発地にし、POI 検索・地図タップ・レイヤから施設を順不同で5件ほど追加して最適化すると、地図上で無駄な往復のない順序になる。
- 最適化中に画面を閉じても、一覧が中途半端に変わらない。
- `geo-routes:OptimizeWaypoints` を許可していないキーで、権限の追加を促す案内が出る。

## 6. 想定されるリスク

- **実機と実 API を確認できない**：応答の形式はドキュメントの例をもとに実装する。地点の対応付けは自前の ID で行い、ID が欠けている・重複している応答はエラーとして扱い、一覧を壊さないようにする。実機確認は利用者に依頼する。
- **範囲の上限と料金**：全地点を囲む矩形の周長が 500 km を超えると最適化できない。200 km を超えると料金区分が Premium になる。エラー時に上限と対処を案内し、料金は README に明記する。
- **スイッチの意味が伝わらない**：オフのとき、最後に追加した地点が終点でなくなることがある。スイッチの下に補足文を置き、結果は一覧と地図の番号で確認できるようにする。
- **画面の縦方向が長くなる**：「訪問順」に操作が増える。操作部は地点が並べ替え可能な数になったときだけ表示する。
- **README の画像が古くなる**：`img/visit-order-editor.png` は UI の変更で実際の画面と合わなくなる。この環境では撮り直せないため、撮り直しは利用者に依頼する。

## 7. 今後の検討事項（設計フェーズで詳細化）

- `OptimizeWaypoints` の応答で、出発地・目的地が `OptimizedWaypoints` に含まれるかどうかと、その ID の形式（ドキュメントの例で確認する）。
- 範囲超過の判定方法：リクエスト前にクライアントで弾くと境界付近で誤判定するおそれがある。HTTP 400 を受けたあとに距離を計算して原因を推定する方式を検討する。
- 「訪問順」内の配置：スイッチ、最適化ボタン、「元の順序に戻す」、結果の表示位置。
- 最適化後の総距離・所要時間を、トーストだけにするか、画面内にも残すか。
- 取り消し用の状態の持ち方と、`onStopsChanged` での破棄の条件。
